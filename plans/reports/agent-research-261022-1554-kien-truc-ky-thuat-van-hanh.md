## 1. Durability & correctness for single-site on-premise SQLite

DuriOS currently opens SQLite at `src/storage/sqlite-client.ts` with three PRAGMAs: `journal_mode = WAL`, `foreign_keys = ON`, `busy_timeout = 5000`. It never sets `PRAGMA synchronous`.

**C-1. SUPPORTED — SQLite's default `synchronous` is FULL, so unconfigured bun:sqlite is fully durable per commit.**
Source: SQLite, "Compile-time Options and Enabling Performance-Enhancing Optimizations", https://www.sqlite.org/compile.html (accessed 2026-10-22). "This macro determines the default value of the PRAGMA synchronous setting. If not overridden at compile-time, the default setting is 2 (FULL)." Reasoning: Bun's `bun:sqlite` compiles SQLite without overriding this macro, so DuriOS inherits FULL. That means each commit fsyncs the WAL. The project's durability posture is stronger than the common Bun example (which sets `NORMAL`), and no code change is required for correctness — only explicit documentation of the invariant.

**C-2. SUPPORTED — In WAL mode with `synchronous=FULL`, SQLite is ACID; with `NORMAL` it can lose committed transactions on power loss but cannot corrupt the file.**
Sources: (a) SQLite, "PRAGMA journal_mode / PRAGMA synchronous", https://www.sqlite.org/pragma.html#pragma_synchronous, "FULL is atomic, consistent, isolated, and durable (ACID) in WAL mode"; (b) https://www.sqlite.org/pragma.html#pragma_wal_checkpoint, "in WAL mode, the WAL file is synced before each checkpoint and the database file is synced after each completed checkpoint"; (c) Bun, "SQLite — bun:sqlite", https://bun.sh/docs/api/sqlite, "A power loss can lose the last commits, but it cannot corrupt the database." (secondary, vendor doc). Reasoning: the two failure modes are distinct and must not be conflated. Losing the last commit is a durability gap (relevant to a regulated ledger where a verified approval must survive a power cut); corruption is a consistency gap (far more damaging because it destroys evidence wholesale). DuriOS is on FULL, so neither applies — this is the correct setting for a regulated single-site custodian.

**C-3. SUPPORTED — The documented dominant corruption causes are outside SQLite's control: file overwrite, lock violations, failure to sync, and hardware that lies about fsync.**
Source: SQLite, "How Corruption Can Happen", https://sqlite.org/howtocorrupt.html. Direct quotes: "SQLite database files are ordinary disk files. ... There is nothing that the SQLite library can do to defend against this."; "most consumer-grade mass storage devices lie about syncing."; "Pulling out the memory stick while the LED is still flashing will frequently result in database corruption." Reasoning: this is the operational risk profile for Cai Lậy. The realistic threats are an operator copying a live DB file, deleting a hot journal/WAL after a crash, running SQLite over a network filesystem, or using cheap flash. None of these are fixed by schema design; they require the runbook that GATE-04 exercises.

**C-4. SUPPORTED — Copying a live database file can produce a corrupt backup; the backup API or `VACUUM INTO` is the safe path.**
Sources: (a) SQLite, "Online Backup API", https://sqlite.org/backup.html: an online backup "can be done incrementally" so the source is locked "only for the brief periods of time when it is actually being read from". (b) SQLite, "VACUUM", https://sqlite.org/lang_vacuum.html: "The VACUUM command with an INTO clause is an alternative to the backup API for generating backup copies of a live database" and "all deleted content is purged from the backup, leaving behind no forensic traces." Contrast with howtocorrupt.html: a copy taken mid-write "might contain some old and some new content, and thus be corrupt." Reasoning: DuriOS's GATE-04 `verifySiteBackup` already requires "100% blob SHA-256 match", which is a hash check but not necessarily a consistency check. The backup must be produced by the API or `VACUUM INTO`, not by `cp`, and then hash-verified.

**C-5. SUPPORTED — `VACUUM INTO` output can itself be incomplete and corrupt if interrupted, and it changes ROWIDs.**
Source: SQLite, "VACUUM", https://sqlite.org/lang_vacuum.html: if interrupted by unplanned shutdown, "the generated output database might be incomplete and corrupt"; if `synchronous` is NORMAL or FULL the output is flushed so a *post-completion* power failure "should not corrupt the database". Also: "The VACUUM command may change the ROWIDs of entries in any tables that do not have an explicit INTEGER PRIMARY KEY." Reasoning: DuriOS's `audit_events` uses `sequence_id INTEGER PRIMARY KEY AUTOINCREMENT`, so ROWIDs are stable — but `export_manifests` and `container_dossiers` use `TEXT PRIMARY KEY`, and their ROWIDs would shift in a vacuumed backup. That does not break the hash chain (which does not cover ROWIDs) but does mean a backup and its source are not byte-comparable; comparison must be logical, not bytewise.

**C-6. PARTIALLY_SUPPORTED — WAL mode is safe from corruption under synchronous=NORMAL, but only checkpointing is the remaining corruption vector.**
Source: SQLite, "How Corruption Can Happen", https://sqlite.org/howtocorrupt.html: "In WAL mode, the only time that a failed sync operation can cause database corruption is during a checkpoint operation." and "A sync failure during a COMMIT might result in loss of durability but not in a corrupt database file." Defense given: "to use SQLite in WAL mode and to checkpoint as infrequently as possible." Reasoning: DuriOS uses SQLite's default autocheckpoint of 1000 pages (SQLite, "PRAGMA wal_autocheckpoint", https://www.sqlite.org/pragma.html#pragma_wal_autocheckpoint). For a low-write single-site ledger, checkpoint frequency is not a throughput concern, so no tuning is needed — but automatic checkpoints are all PASSIVE, and "if there is a long-running reader, the WAL will grow indefinitely" (same page), so unbounded WAL growth is a real disk-exhaustion failure mode for a site that never restarts.

**C-7. SUPPORTED — SQLite permits only one writer at a time, and `BEGIN IMMEDIATE` is the recommended way to make write contention deterministic under `busy_timeout`.**
Source: SQLite, "Result Codes", https://www.sqlite.org/rescode.html#proto: "SQLite allows only one writer at a time"; "Use `BEGIN IMMEDIATE`, not `BEGIN`, for write transactions"; with IMMEDIATE "SQLite guarantees that no subsequent operations on the same database through the next COMMIT will return SQLITE_BUSY." Reasoning: DuriOS sets `busy_timeout = 5000`, which converts contention into a 5-second wait rather than an instant failure. Because the audit ledger's `recordEvent` wraps a read-of-last-hash plus an insert in a single transaction, this is the right shape — but if any caller used a deferred `BEGIN`, the read-then-write could hit `SQLITE_BUSY` mid-transaction and abort a partially appended chain segment. Flagging as a code-review item rather than a proven defect, since I did not trace every call site.

## 2. Tamper-evident audit trails: hash chain, signing, transparency logs, WORM

DuriOS's ledger is a SHA-256 hash chain (`src/storage/sqlite-audit-ledger.ts`) with a `GENESIS-` sentinel, `previous_hash`/`event_hash` columns, and `verifyIntegrity()` recomputing the chain top to bottom. There is no signature and, critically, no database-level immutability constraint on `audit_events`.

**C-8. SUPPORTED — A hash chain detects tampering only if the verifier holds a trusted anchor outside the chain and the attacker cannot recompute the whole chain.**
Sources: (a) DuriOS code, `src/storage/sqlite-audit-ledger.ts`: `verifyIntegrity()` starts from `GENESIS_HASH` and walks forward; any single-row edit fails. (b) Russ Cox, "Transparent Logs for Skeptical Clients", https://research.swtch.com/tlog (maintainer blog, Google): a lone hash "bootstraps a small amount of trusted data into a much larger amount of data" but verification "requires hashing the entire data set." Reasoning: `verifyIntegrity()` is a genuine tamper-evidence control against an edit to a *single* event. But because the genesis value is a hardcoded constant in the same file as the verifier, an attacker who can write to the database can also rebuild the entire chain from a chosen genesis and pass verification. The chain is only meaningful against an outside auditor if the terminal hash (or a signature over it) is published or anchored somewhere the attacker does not control. This is exactly what `src/saas/cloud-ledger-anchor.ts` appears intended for.

**C-9. SUPPORTED — A signed transparency log (Merkle tree) provides two proofs a hash chain cannot: compact inclusion, and compact consistency that makes a rewritten history detectable.**
Source: RFC 6962, "Certificate Transparency", Laurie/Langley/Kasper, June 2013, https://www.rfc-editor.org/rfc/rfc6962.html. §1: "if a log attempts to show different things to different people, this can be efficiently detected by comparing tree roots and consistency proofs"; §2.1.2: "Merkle consistency proofs prove the append-only property of the tree"; §7.3: "As soon as two conflicting Signed Tree Heads for the same log are detected, this is cryptographic proof" of misbehaviour. Reasoning: with a chain, two observers holding divergent views have no cheap way to tell whether one extends the other — the heads are opaque accumulators. A consistency proof is O(log n). For DuriOS this is the difference between "we believe our ledger was not rewritten" and "we can prove, to a third party, that the ledger we show is the same one they saw."

**C-10. SUPPORTED — SCITT is the supply-chain generalization of Certificate Transparency and explicitly targets this use case; it makes append-only, non-equivocating, replayable logs a MUST, and receipts verify offline.**
Source: IETF draft-ietf-scitt-architecture-16, "An Architecture for Trustworthy Computing", https://www.ietf.org/archive/id/draft-ietf-scitt-architecture-16.html (accessed 2026-10-22). Direct quotes: "a scalable architecture for single-issuer signed statement transparency applicable to any supply chain"; a VDS must be append-only ensuring "that the Statement Sequence cannot be modified, deleted, or reordered", non-equivocating, and replayable; receipts are "universally verifiable without online access to the TS"; "SCITT is a generalization of Certificate Transparency (CT)." Reasoning: this maps directly onto DuriOS's planned "verified organisations share attestations" network layer. Note honestly: SCITT is an IETF draft, not an RFC — adopting it is adopting an in-flight standard, which carries churn risk (see Adoption Risk below).

**C-11. SUPPORTED — NIST IR 8374r1 recommends storing data in immutable format and keeping an offline backup copy.**
Source: NIST IR 8374r1, "Ransomware Risk Management: A Cybersecurity Framework 2.0 Community Profile", June 2026, https://doi.org/10.6028/NIST.IR.8374r1 (supersedes IR 8374, withdrawn 2026-06-11). Quotes: "Store data in an immutable format (so that the database does not automatically overwrite older data when new data is made available). (PR.DS-11)"; "Back up data, secure backups, and test restoration."; "Regular backups that are maintained and tested are essential to timely and recovery from ransomware events. Backups should have a copy stored offline or otherwise in a manner that prevents access to them by the attacker or compromise by ransomware." Reasoning: this is the direct authority for two concrete changes to DuriOS. First, the `audit_events` table needs an append-only enforcement mechanism (SQLite triggers rejecting UPDATE/DELETE, plus a schema-level or deployment-level guard), not just application-level discipline. Second, a backup that lives only on the same machine as the live DB does not satisfy the offline-copy recommendation, and a site that is the sole custodian of its data has no cloud fallback.

**Verdict on "when is a hash chain sufficient":** For a single site that is the sole custodian, the hash chain plus a signed, offsite-anchored terminal digest is defensible and proportionate. A full transparency log is required only once *multiple mutually distrustful verifiers* must be able to detect a rewritten history — which is precisely the state DuriOS is planning to enter with the attestation-sharing network. My recommendation is therefore not to adopt RFC 6962/SCITT at the site level, but to anchor the existing chain's terminal hash into whatever the sharing layer uses, so the site-level evidence and the network-level evidence share one trust root.

## 3. Human-in-the-loop verification of extracted fields

DuriOS models this well structurally: `ExtractedField` carries `confidenceScore` and `FieldVerificationStatus` of `DRAFT | HUMAN_VERIFIED | REJECTED`, with `verifiedBy`/`verifiedAt`, and `src/verification/hitl-service.ts` requires an `AuthenticatedActor` so no machine-only approval path exists.

**C-12. UNVERIFIABLE — There is no single published accuracy figure for LLM/OCR extraction of structured fields from invoices, certificates, and customs documents that generalizes to DuriOS's document set.**
Attempted and failed sources: Google Cloud Document AI docs (redirected to docs.cloud.google.com, then 404), Azure Document Intelligence accuracy page (https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/concept/accuracy-confidence — reachable but reports *only* that confidence scores exist and are hierarchical; it publishes no accuracy percentage), AWS Textract limits page (returned only a page anchor with no content), arXiv IDs I tried (all were unrelated papers). Reasoning: I am reporting this as unverified rather than inventing a number. The honest position is that vendor IDP accuracy is document-corpus-dependent and is published as per-model confidence, not as a single error rate. Any accuracy number for DuriOS must be measured on the pilot corpus at Cai Lậy, which is what GATE-05's "5 real files with arithmetic mean under 300 seconds and at least 2 blind-planted errors all caught" is actually designed to produce.

**C-13. SUPPORTED — Confidence scores are hierarchical (cell, row, table) and a high cell score does not imply a correct row.**
Source: Microsoft, "Interpret and improve model accuracy and confidence scores" (Azure AI Document Intelligence), https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/concept/accuracy-confidence (published as doc-intel-4.0.0), accessed 2026-10-22. Quotes: "A correctly predicted cell that belongs to a row with other possible misses would have high cell confidence, but the row's confidence should be low."; "the expectation for merged cells is to have lower confidence values". Reasoning: DuriOS uses a single flat `confidenceScore: number` per `ExtractedField`. For table-like documents (packing lists, lab test reports, phytosanitary line items), a flat score cannot distinguish "this individual value is well-recognized" from "the row it belongs to is structurally suspect". This matters specifically because a plausible-looking wrong value with high local confidence is the classic failure mode that defeats value-only verification.

**C-14. SUPPORTED — Regulated record-keeping practice is that transcribed data be verified against the source by a second check; NIST IR 8374r1 frames this as accuracy and human oversight, not as a numeric tolerance.**
Sources: (a) NIST IR 8374r1 (as above) requires controls ensuring data accuracy and integrity (PR.DS family). (b) EU GMP Annex 11 and FDA Data Integrity guidance were both unreachable in this session (403/404 on every URL I tried, including the EC and FDA hosts), so I could not quote their specific second-person-verification paragraph and am not going to reconstruct it from memory. Reasoning: the standard practice — that a transcription is checked against source, ideally by a second person, and that the check is attributable — is captured by DuriOS's mandatory HITL with `verifiedBy`. The gap is that DuriOS does not distinguish *independent double entry* (two people enter the same field and disagreements are reconciled) from *second-person verification* (one person enters, another confirms). For a document with a critical figure (net weight, container number, lab result), the packhouse workflow does the former in paper practice.

**Recommendation (3):** DuriOS should not chase a vendor accuracy figure. It should (a) block approval on fields whose confidence falls below a threshold derived from the GATE-05 pilot measurement rather than a guessed constant; (b) treat `LAB_TEST_REPORT` and `PHYTOSANITARY_CERTIFICATE` numeric fields as requiring second-person confirmation, distinct from a single clerk's confirmation; and (c) record whether a verification was a pure confirmation or a manual edit — which the ledger already does via `FIELD_HUMAN_VERIFIED` vs `FIELD_MANUALLY_EDITED`.

## 4. Digital signature and key management for offline deployments

Current implementation: `src/saas/workspace-portability-bundle.ts` computes a payload SHA-256 and, if a secret of length >= 16 is supplied, an HMAC-SHA256 over the payload digest, compared with `timingSafeEqual`. The secret is read from `DURIOS_PORTABILITY_HMAC_SECRET`.

**C-15. SUPPORTED — HMAC and digital signatures provide different security services: NIST explicitly binds non-repudiation to asymmetric signature keys, not to symmetric authentication keys.**
Source: NIST SP 800-57 Part 1 Rev. 5, "Recommendation for Key Management: Part 1 — General", May 2020, https://doi.org/10.6028/NIST.SP.800-57pt1r5. §5.1.1: "Private signature keys are the private keys of asymmetric-key (public-key) key pairs ... When properly handled, private signature keys can be used to provide source authentication and integrity authentication as well as support the non-repudiation of messages, documents, or stored data." By contrast §3.5 ties non-repudiation to "digital signature keys and digital certificates", and §3.5 also warns: "A real determination of non-repudiation is a legal decision with many aspects to be considered. Cryptographic mechanisms can only be used as one element in this decision." Reasoning: an HMAC proves *integrity* and *that both parties share a secret*. It cannot prove to a Chinese importer or a customs officer *which* packhouse produced a bundle, because every party holding the secret could have produced it. Since DuriOS's stated goal is that an importer or China customs can verify integrity independently, HMAC-SHA256 alone does not meet that goal. This is the single most consequential finding in this angle.

**C-16. SUPPORTED — HMAC-SHA-256 provides 128 bits of security strength and is approved; RSA at 2048 bits does not exceed 112 bits and is below SHA-256's strength.**
Source: NIST SP 800-57pt1r5 Table 3 ("Maximum security strengths for hash and hash-based functions"): SHA-256 is listed for 128-bit security for collision-resistant applications, and "SHA-256 ..." appears in the HMAC/KMAC column for the ">= 256" row. Table 2 lists AES-128 at 128 bits, k = 3072 (RSA) at 128 bits, and k = 2048 at 112 bits. The text confirms: "a 2048-bit RSA key cannot provide more than 112 bits of security strength even though SHA-256 can support a security strength of 128 bits (see Tables 2 and 3) when used for digital signature". Reasoning: HMAC-SHA256 is not weak — at 128 bits it is squarely approved. The problem is the *property* it provides (C-15), not its strength.

**C-17. SUPPORTED — EdDSA is approved in FIPS 186-5, with Ed25519/Ed448 specified by reference to RFC 8032; RSA requires a modulus of at least 2048 bits.**
Source: NIST FIPS 186-5, "Digital Signature Standard (DSS)", published February 3, 2023, https://doi.org/10.6028/NIST.FIPS.186-5. Body statements: "The Edwards Curve Digital Signature Algorithm (EdDSA) is specified in IETF RFC 8032 [6]. FIPS 186-5 approves the use of EdDSA and specifies additional requirements." and "This standard specifies the use of a modulus whose bit length is an even integer and greater than or equal to 2048 bits." Reasoning: DuriOS already uses Ed25519 for its commercial licence keys, so a signature-based export bundle is consistent with existing practice. Curves for federal use are named in SP 800-186, which I did not need to consult for this recommendation.

**C-18. REFUTED (as a claim about the code) — A client-supplied `portabilitySecret` in the HTTP request body allows self-attesting verification.**
Source: DuriOS code, `src/server/open-core-portability-handler.ts`, `handleVerifyWorkspacePortability`: `const secret = typeof body.portabilitySecret === "string" && body.portabilitySecret.trim().length > 0 ? body.portabilitySecret.trim() : process.env.DURIOS_PORTABILITY_HMAC_SECRET?.trim();`. Reasoning: any caller can POST an arbitrary secret and an HMAC computed with that same secret, and `verifyWorkspacePortabilityBundle` returns `{valid: true}`. The server enforces nothing about the secret's provenance. In a product whose value proposition is that an independent party can check integrity, an endpoint that endorses self-signed claims is actively harmful — it produces "verified" badges for arbitrary payloads. This is a correctness defect in a public contract, not a hardening suggestion, and it should be closed before any external verifier is pointed at it.

**C-19. PARTIALLY_SUPPORTED — FIPS 140-3 provides a validation framework with four qualitative security levels, but an HMAC key is not protected by it.**
Source: NIST FIPS 140-3, "Security Requirements for Cryptographic Modules", published March 22, 2019, https://csrc.nist.gov/pubs/fips/140-3/final. It offers "four increasing, qualitative levels of security" and aligns with ISO/IEC 19790:2012 and ISO/IEC 24759:2017. Reasoning: FIPS 140-3 validates a *module*, including "sensitive security parameter management" and "software/firmware security". A TypeScript application calling Bun's bundled crypto is validated as part of Bun only insofar as its own cryptography is approved — an application cannot be "FIPS certified" by itself. So the honest guidance for DuriOS is: use approved primitives from an approved implementation (HMAC-SHA256 and Ed25519 are approved algorithms), and do not claim FIPS 140-3 compliance.

**What happens when a site key leaks — the honest answer:** For HMAC, a leak is total and reciprocal. The secret signs bundles *and* verifies them, so a leaked secret both lets an attacker forge valid-looking bundles and lets any holder impersonate the site. There is no revocation path: you must rotate the secret, and every previously issued bundle loses verifiability (there is no way to distinguish "signed before rotation" from "forged"). Add to this that DuriOS has no documented key-rotation mechanism for `DURIOS_PORTABILITY_HMAC_SECRET` — rotation means re-issuing the secret, regenerating bundles, and the export history stays verifiable only against the old secret. For an asymmetric scheme, a leaked *private* key lets an attacker forge but does **not** let anyone verify-as if they held the private key, and you can publish a revocation / a new public key while old bundles remain verifiable against the old public key. This asymmetry is the whole reason the switch matters.

**Recommendation (4):** Move export integrity to Ed25519 detached signatures, with the public key published and versioned alongside the bundle so old bundles remain verifiable after rotation. Keep HMAC-SHA256 only for non-repudiation-irrelevant internal integrity checks. Remove the client-supplied secret path entirely. Store the site private key in an OS-protected secret store (macOS Keychain or a TPM-backed slot), never in `.env` committed to disk, and document a rotation runbook with an explicit cutover date. Note the tension honestly: for a *local-first, sole-custodian* site, the packhouse must hold the private key, so a hostile site admin can always sign — asymmetric signing raises the bar (it needs key exfiltration, not just a leaked env var) but does not remove the threat. That residual risk is inherent to on-premise and should be stated as such rather than hidden.

## 5. Agri-food traceability data standards to adopt rather than invent

I grepped the source tree for `GS1|EPCIS|ePhyto|WCO|VietGAP`: **zero matches**. DuriOS invents its own identifiers (`dossierCode`, `containerNumber`, `fieldKey`) with no external standard binding. That is a defensible Stage-0 choice but it forecloses interoperability exactly where the business case depends on it.

**C-20. SUPPORTED — GS1 EPCIS 2.0 is a ratified GS1 standard (June 2022) defining exactly the event model a packhouse produces, and it has no ISO counterpart.**
Source: GS1, "EPCIS 2.0", Release 2.0, Ratified, Jun 2022, https://ref.gs1.org/standards/epcis/2.0.0/standard/ (PDF retrieved and text-extracted). §7.2: "This module defines six event types, one very generic event and five subclasses ... ObjectEvent ... AggregationEvent ... TransactionEvent ... TransformationEvent ... AssociationEvent". Reasoning: DuriOS's dossier lifecycle (ingest documents -> aggregate into a container dossier -> transform via verification -> transact on export) maps almost one-to-one onto EPCIS's AggregationEvent/TransformationEvent/TransactionEvent. Adopting EPCIS field names would let a downstream importer's existing GS1 tooling consume DuriOS output. Caveat honestly: I found no ISO standard corresponding to EPCIS, so it is a GS1 standard rather than an ISO one — it is de facto global, not de jure international. GS1's main site also had a TLS certificate misconfiguration (altnames pointed to `*.azureedge.net`), which I worked around via `ref.gs1.org`.

**C-21. SUPPORTED — IPPC ePhyto is the international electronic phytosanitary certificate exchange, XML-based, aligned to ISPM 12 Appendix 1, with a Hub and a GeNS for countries lacking their own system.**
Source: IPPC (FAO), "ePhyto", https://www.ippc.int/en/ephyto/. Quotes: ePhyto certificates are "produced in accordance with ISPM 12 including Appendix 1"; components are "a central server (Hub)", "a web-based system that can produce and receive ePhytos" (GeNS), and harmonized "standardized mapping, codes and lists". Page also points to www.ephytoexchange.org for joining. Reasoning: DuriOS models `PHYTOSANITARY_CERTIFICATE` as a document type. The certificate's regulated content is defined by ISPM 12 Appendix 1, and the exchange format is the IPPC XML schema. DuriOS should carry those specific data elements rather than free-form extracted fields. Limitation: the ephytoexchange.org site is JavaScript-rendered and returned no parseable content in this session, so **I could not verify the count of connected NPPOs or whether Vietnam specifically exchanges ePhyto, nor whether an ASEAN regional hub exists.** That is a genuine gap and it is the single most valuable thing to resolve next, because Vietnam's actual mechanism (ePhyto vs. paper vs. bilateral arrangement) determines whether emitting IPPC-shaped XML has real value.

**C-22. SUPPORTED — The WCO Data Model Version 4 is the customs interoperability standard, aligned with UN/TDED and UN/CEFACT, and now supports JSON and APIs.**
Source: WCO, "WCO Data Model", https://www.wcoomd.org/en/topics/facilitation/instrument-and-tools/tools/data-model.aspx. Quotes: "the data foundation for global trade interoperability for over two decades"; aligns with "the United Nations Trade Data Elements Directory (UN/TDED) and draws on UN/CEFACT and ISO standards"; "Version 4, the latest iteration, introduces substantial enhancements" including "support for the JSON message format and APIs"; components include "Information Packages (subsets of the WCO DM)" and "Code lists and electronic messages". Reasoning: DuriOS's GACC-facing container reconciliation is exactly a customs-data problem, and the WCO DM is what national single-window systems are built on. Since Version 4 supports JSON, an on-premise TypeScript system can conform without XML tooling.

**On Vietnamese/ASEAN fruit export specifically:** I found no usable in-session evidence on which of these are actually in use for Vietnamese durian export. My attempts at Vietnamese legal-document hosts (vanban.chinhphu.vn, thuvienphapluat.vn) returned 404/403, and a targeted search for Decree 154/2025 could not be confirmed. **I am not going to assert a Vietnamese decree number I cannot verify.** The defensible statement is: China is >95% of Vietnam's durian export per the project's own cited Bộ NN&MT briefing (2026-09-03), the GACC registry is the operative counterparty, and therefore the WCO Data Model plus GACC's own field requirements are the binding interoperability targets — with EPCIS as the internal event vocabulary and IPPC/ISPM 12 Appendix 1 as the phytosanitary content standard. Whether ePhyto is the actual Vietnamese exchange channel remains open.

## 6. Multi-tenant RBAC, tenant isolation, and on-prem backup/DR

**C-23. SUPPORTED — OWASP's guidance is that plain RBAC is the wrong tool for tenant boundaries; isolation must be enforced per-object at the data layer, and client-supplied tenant IDs are selectors only.**
Source: OWASP Cheat Sheet Series, "Authorization Cheat Sheet", https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html. Quotes: RBAC "is poorly suited for use cases where distinct organizations or customers will need access to the same set of protected resources"; "Perform access control checks on *every* request for the *specific* object or functionality being accessed"; "Horizontal privilege escalation (i.e. being able to access another user's resources) is an especially common weakness". Reasoning: DuriOS's tri-tuple persona RBAC is a *role* model layered over a `tenant_id` column. The enforcement point is per-query filtering (`getEventsForDossier(dossierId, tenantId)`), which is the right shape and matches OWASP's per-object guidance. The risk is that correctness depends on every query remembering `tenant_id`. OWASP's specific warning about trusting a client-supplied tenant identifier applies to any route where tenant is read from a token or header rather than from the authenticated session.

**C-24. SUPPORTED — For a shared-table design, OWASP requires fail-closed tenant scoping, negative tests, and never serving tenant-scoped requests through a privileged connection.**
Source: OWASP Cheat Sheet Series, "Multi-Tenant Application Security", https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html. Quotes: "Treat client-supplied tenant identifiers as selectors only."; "Bind tenant context to a server-verified identity and current tenant membership"; "Fail closed if the tenant context is missing or invalid; do not fall back to an unscoped query."; "Do not serve ordinary tenant-scoped requests through a privileged connection."; "Include the tenant identifier in every cache key whose value or authorization varies by tenant."; on backups: "Restore into a separate resource and selectively recover the target tenant's data" and "Do not give a tenant operator access to a shared backup." Reasoning: DuriOS is a single-site product with three personas, so multi-tenancy is currently one tenant (the packhouse) with role separation, plus a planned network layer for cross-org attestation sharing. The moment that network layer lands, these rules become binding rather than advisory. Two are checkable today: whether any code path falls back to an unscoped query, and whether backup restore is tested per tenant.

**C-25. SUPPORTED — SQLite offers no row-level security; tenant isolation is entirely application-enforced, so the database is not a trust boundary.**
Source: SQLite documentation generally, plus OWASP Multi-Tenant: shared-tables-plus-RLS requires an enforceable policy layer that SQLite does not have (no RLS feature). Reasoning: this is the most important architectural constraint in this angle. In PostgreSQL you could push isolation into the database; in SQLite, any process holding the database file and write access has unrestricted access to all tenants' rows. DuriOS must therefore treat the OS user that owns the SQLite file as the trust boundary, and the GATE-03 loopback-binding requirement is doing real security work. Cross-tenant read protection is only as strong as the filesystem permissions on the single database file.

**C-26. SUPPORTED — For a sole-custodian site, NIST IR 8374r1's offline-copy requirement is not optional, and DuriOS's GATE-04 tests exactly the wrong property if the backup is a same-disk `cp`.**
Sources: NIST IR 8374r1 as above ("Backups should have a copy stored offline or otherwise in a manner that prevents access to them by the attacker"); SQLite backup guidance (C-4, C-5). Reasoning: GATE-04 currently verifies that backup blobs match SHA-256 — i.e. that the backup is a faithful copy. Faithfulness is necessary but not sufficient. A same-disk copy of a corrupt or ransomware-encrypted source is a faithful copy of garbage. The gate should additionally require (a) the backup was produced by the backup API or `VACUUM INTO`, (b) a restore was performed into a separate resource and verified readable, and (c) at least one copy is physically off the site machine. The last item conflicts with a strict local-only/zero-custody posture and is a business decision the founder must make, not a technical one.

## Adoption risk

- **SCITT / RFC 6962 transparency logs:** draft/RFC status. RFC 6962 is Experimental (RFC category) and widely deployed via Certificate Transparency, so de facto stable; SCITT is a draft and can shift. Do not build a dependency on a draft at Stage 0.
- **GS1 EPCIS 2.0:** ratified June 2022, stable, backed by a large standards body. Adoption risk is low, cost is real — conformance is a data-model commitment. Partial adoption (vocabulary alignment) is the low-risk entry point.
- **IPPC ePhyto / ISPM 12 Appendix 1:** mature and government-backed. Risk here is not standard stability, it is not knowing Vietnam's actual exchange channel (unresolved).
- **Ed25519:** already in the codebase for licences, approved in FIPS 186-5. Lowest-risk change in this report.
- **NIST IR 8374r1 is a *profile*, not a mandate** — it maps CSF 2.0 outcomes and requires judgement about which apply. The offline-copy and immutable-format outcomes are the two that bear directly on DuriOS's stated constraints.

## Limitations (what I did not cover and why it matters)

1. **No published accuracy figure for extraction.** Azure, Google, and AWS pages were unreachable or published only confidence semantics. Any accuracy claim for DuriOS must come from the Cai Lậy pilot; do not let vendor marketing numbers be substituted.
2. **EU GMP Annex 11 and FDA Data Integrity guidance not retrieved** — every URL I tried returned 403/404. I deliberately did not reconstruct their second-person-verification wording from memory. If the regulated-record-keeping requirement needs a quotable citation, that is the gap to close.
3. **Vietnamese/ASEAN traceability practice unverified.** Could not confirm which traceability regulations apply, whether Vietnam exchanges ePhyto, or whether an ASEAN regional ePhyto hub exists. This matters most because it determines whether emitting IPPC-shaped XML has real value or is ceremony.
4. **No code review of every `tenant_id` filter or transaction boundary.** The `BEGIN IMMEDIATE` concern (C-7) and a possible unscoped-query fallback (C-24) are flagged as review items, not proven defects.
5. **The `audit_events` immutability claim is structural, not tested.** I read the schema and the verifier; I did not run a tamper test against a live database. "No UPDATE/DELETE guard exists" is read from the DDL, and its exploitability follows from the verifier starting at a hardcoded genesis (C-8).
